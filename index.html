Test design

System under test: BowlingGame with strikes, spares, 10th-frame fill balls and input validation.

Functional

9 tests (F-01 to F-09): gutter game, all ones, spare and strike bonuses, all spares (150), perfect game (300), a mixed game (167).

Boundary

9 tests, 10 runs (B-01 to B-09): 0 and 10 pins, 10th-frame strike, spare and open frames, game-complete edges.

Error and edge

8 tests, 12 runs (E-01 to E-08): -1, 11 and extreme pin counts, frame totals over 10, rolling after the game, scoring too early.

Techniques: equivalence partitioning, boundary-value analysis, error guessing and state-based testing. The suite makes 33 assertion calls (about 38 executed at run time).

How it runs

Every push to GitHub rebuilds and republishes this page.

  1. PushCommit from Eclipse to GitHub.
  2. Testmvn clean verify runs the JUnit 5 suite with the JaCoCo agent.
  3. GateThe build fails below 90% line or 85% branch coverage.
  4. ReportJaCoCo writes the HTML report under coverage/.
  5. DeployGitHub Pages publishes this site.

Takeaways

100% coverage is not the same as correct code. JaCoCo shows what ran, not whether the assertions checked the right result. A test with no assertions can execute the same lines and catch nothing, which is why the seeded-defect experiment matters.

What JaCoCo measured well

No source changes were needed, the report appears in seconds as part of mvn verify, and branch-level detail made it easy to see that all 38 decision outcomes are exercised.

Limits to keep in mind

It does not measure requirement coverage or test-data quality, and branch coverage counts decision outcomes rather than condition combinations. Mutation testing (for example PIT) is the natural next step.
